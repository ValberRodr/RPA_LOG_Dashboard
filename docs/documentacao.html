RPA Ops Monitor

Referência técnica completa do painel de observabilidade de RPAs: arquitetura, pipeline de dados, todas as classes do backend e do frontend, modelo de dados, integração opcional com a Automation Anywhere 360 Control Room, testes automatizados e o runbook de sustentação. Escrita para quem vai manter e evoluir o código, não para o usuário final do dashboard.

Python 3 · stdlib apenas JavaScript vanilla · sem build/bundler Zero dependências externas Somente 127.0.0.1 10 RPAs · 11 VMs (base sintética)

Introdução#

O RPA Ops Monitor é um painel de observabilidade para uma esteira de RPAs (Robotic Process Automation) operando em VMs dedicadas. Ele lê os arquivos de log gerados pelas próprias automações e pela telemetria das máquinas, calcula indicadores operacionais (SLA, duração, retries, confiabilidade de infraestrutura, Pareto de erros, sugestão de consolidação de VMs) e apresenta tudo em um cockpit único, com telas de drill-down para investigação técnica.

O projeto é deliberadamente sem dependências externas: o backend é um único processo Python usando apenas a biblioteca padrão (http.server), e o frontend é JavaScript clássico servido diretamente pelo mesmo processo — sem Node, sem bundler, sem framework, sem CDN. Essa escolha de arquitetura é o que permite rodar em qualquer estação com Python 3 instalado, sem instalação de pacotes e sem acesso à internet.

i

Este documento assume que quem o lê já sabe o que o produto faz operacionalmente (a UI é autoexplicativa). O foco aqui é como o código está organizado, por que certas decisões foram tomadas e onde mexer para cada tipo de mudança.

Módulos opcionais

Há um único módulo aditivo e removível no projeto: a integração com a Automation Anywhere 360 Control Room (assets/aa-integration.js + AutomationAnywhereGateway em server.py). Remover as duas tags (<link>/<script>) de index.html devolve o dashboard exatamente ao estado anterior à integração — nenhum dado, cálculo ou fluxo do cockpit original depende dela.

Fluxo de dados#

Tudo no painel deriva de três fontes em disco: os logs de execução consolidados por dia, os logs de eventos por execução, e a telemetria de VM. Nada é persistido em banco — cada requisição HTTP relevante decide se precisa reprocessar (ver cache e invalidação) e, quando precisa, o pipeline abaixo roda por completo.

logs/*.log, logs/*.jsonl
Execuções, eventos por etapa, telemetria de VM — filtrados por nome de arquivo ANTES de abrir (janela de datas)
DatasetBuilder.build_dataset(mode)
obs — dataset "de detalhe"
executions, eventsByExecution, vmContextByExecution, rpaAggregates, recurrenceByExecution, dependencyStatus, loadIssues, loadStats
IndexBuilder.build_index(obs, …)
index — dataset "agregado"
rpas (estado operacional), trend, timeline, incidents, alerts, vms, vmUtilization, vmReliability, vmConsolidation, errorParetos, summary
GET /assets/observability-data.js
window.OBS_DATA = obs
GET /assets/index-data.js
window.INDEX_DATA = index
Frontend
index.html lê DATA (= INDEX_DATA); as 3 páginas avulsas leem window.OBS_DATA/window.INDEX_DATA via window.RPAUI

O obs ("detalhe") e o index ("agregado") são gerados juntos numa única chamada — build_dataset monta obs e, ao final, chama build_index(obs, …) internamente. Isso significa que os dois arquivos servidos ao navegador são sempre consistentes entre si (mesmo snapshot, mesma janela de tempo).

O parâmetro ?mode=90d nas duas tags <script> estáticas do primeiro carregamento de cada página garante que abrir o app sempre volta ao padrão de 90 dias, mesmo que uma sessão anterior tenha deixado "histórico completo" em cache no processo do servidor. O refresh incremental (reloadData) busca sem esse parâmetro, preservando o modo que o usuário escolheu na sessão atual.

Escopo léxico compartilhado (leia antes de mexer no frontend)#

!

Isto é a regra mais importante deste documento. index.html carrega assets/dashboard-app.js e, depois, assets/aa-integration.js como duas tags <script> clássicas — sem type="module" e sem nenhuma envolvida por IIFE. Scripts clássicos no mesmo documento compartilham um único ambiente léxico de topo: toda let/const/class/function declarada em dashboard-app.js fica visível, por nome, para aa-integration.js carregado em seguida.

aa-integration.js depende disso para ler, por nome puro, sem nenhuma importação: DATA, $, $$, escapeHtml, showToast, goToPage, fmtDateTime, fmtTime, window.OBS_DATA, window.DATA. Envolver dashboard-app.js num IIFE, ou convertê-lo para type="module" (módulos ES têm escopo próprio, não vazam para o escopo global), faz esses identificadores desaparecerem e quebra a integração inteira silenciosamente — sem erro de sintaxe, só chamadas para undefined.

Por que as classes não resolveram isso

A conversão para OOP (ver Referência de classes) moveu cada função solta para dentro de uma classe como static, mas preservou o alias de nível superior para cada uma (ex.: const escapeHtml = Fmt.escapeHtml;) exatamente por causa desta dependência — sem os aliases, seria preciso reescrever aa-integration.js inteiro para chamar Fmt.escapeHtml(...) em vez de escapeHtml(...), e o próprio módulo AA teria que virar um "consumidor consciente" das classes internas do dashboard, acoplamento que o projeto evita de propósito.

js// fim de assets/dashboard-app.js — um alias por função que existia solta antes
const escapeHtml = Fmt.escapeHtml;
const showToast  = UiFeedback.showToast;
const goToPage   = NavigationController.goToPage;
// ... (lista completa em #padrao-alias)

// aa-integration.js (carregado DEPOIS, mesmo documento) lê essas mesmas
// variáveis de topo por nome, em tempo de chamada:
showToast('Automation Anywhere conectado.');
goToPage('aa-control-room');

Regra prática para PRs futuros: nunca adicione type="module" a dashboard-app.js, nunca envolva o arquivo inteiro numa função IIFE, e ao renomear qualquer identificador de topo (função, classe, alias) grep em assets/aa-integration.js antes de finalizar a mudança.

A mesma regra vale, num nível mais restrito, para observability-core.js: ele é envolvido por uma IIFE própria, mas de propósito — expõe deliberadamente um único ponto de contato, window.RPAUI, para as 3 páginas avulsas. Trocar qualquer chave desse objeto (D, esc, getRpa, etc.) quebra as três páginas ao mesmo tempo.

Cache e invalidação#

Há dois níveis de cache no backend, ambos em memória (nada em disco além dos próprios logs):

1. Cache do dataset completo — DataCache.get_data(mode)

Guarda o último par (obs, index) construído, junto de um fingerprint barato: contagem de arquivos .log/.jsonl em RPA_LOG_ROOT/VM_ROOT, o mtime mais recente e o tamanho total somado — tudo via os.walk + stat(), sem ler conteúdo. Uma requisição repetida sem nada alterado em disco retorna o cache sem tocar nos arquivos.

pythonfp = (count, newest, size)
if _cache['obs'] is None or _cache['fingerprint'] != fp or _cache['mode'] != effective_mode:
    obs, index = build_dataset(effective_mode)
    _cache.update({'fingerprint': fp, 'mode': effective_mode, 'obs': obs, 'index': index})
return _cache['obs'], _cache['index']

2. Cache por arquivo — LogFileReader._read_cached(path)

Mesmo quando o fingerprint global muda (um arquivo novo apareceu, por exemplo), a maioria dos arquivos antigos não mudou — _file_cache guarda, por caminho, {mtime_ns, size, rows} e só reabre/reparseia um arquivo se mtime ou size mudaram desde a última leitura. Isso é o que torna um refresh incremental barato mesmo com centenas de arquivos de log acumulados.

!

Os dois caches são por processo, não por modo isoladamente — trocar de 90d para full invalida o cache do dataset completo (o fingerprint por si só não muda, mas _cache['mode'] muda, forçando reconstrução). Já _file_cache nunca é limpo por modo: um arquivo lido em modo 90d permanece em cache e é reaproveitado se a mesma janela pedir de novo em modo full.

Reconstrução incremental no frontend

RpaDataStore.reloadData(mode) (chamada pelo botão "Recarregar dados" e pelo refresh automático de 20 min) nunca recarrega a página inteira: chama /api/reload, sonda /api/load-status a cada 350 ms até a fase virar concluido/erro, e então rebusca só os dois scripts de dados com um <script> temporário (fetchScript) — preservando página ativa, filtros e posição de scroll.

DatasetBuilder.build_dataset e IndexBuilder.build_index foram deliberadamente mantidos como um único método sequencial cada um (não fragmentados em vários métodos menores). O fluxo é de passagem única com dezenas de variáveis locais interdependentes (execuções → eventos → telemetria → agregados → Pareto → alertas, nessa ordem, cada etapa lendo o resultado da anterior); fatiar mais aumentaria o risco de regressão sem ganho real de legibilidade. Classificação de confiabilidade de VM — o algoritmo

VmReliabilityClassifier._classify_vm_reliability só consegue distinguir "problema da máquina" de "problema de uma RPA específica" quando a VM é compartilhada por mais de uma RPA com amostra suficiente (min_samples=3 execuções). Fluxo de decisão:

CondiçãoClassificação
Menos de 5 execuções no total na VMDADOS_INSUFICIENTES
≤ 1 RPA com amostra confiável (≥3 execuções)ATENÇÃO se taxa de erro geral ≥ 15%, senão SAUDÁVEL
Taxa geral ≥ 15% e dispersão entre RPAs < 15 pontosPROBLEMA_GERAL — todas as RPAs sofrem parecido, aponta para a máquina
Dispersão ≥ 15 pontos e pior RPA ≥ 15% de erroPROBLEMA_ESPECIFICO — concentrado numa RPA, a VM provavelmente não é a causa
Nenhuma das anterioresSAUDÁVEL

Sugestão de consolidação de VMs — o algoritmo

VmConsolidationPlanner constrói, para cada RPA, uma janela de ocupação estimada (duração P95 histórica, não a nominal, + 5 min de margem) para cada horário de agenda. Duas RPAs "conflitam" se alguma combinação de janelas se sobrepõe considerando que o calendário weekdays está contido em daily (qualquer par pode cair no mesmo dia útil — por isso o teste de conflito soma/subtrai 1440 min para cobrir a virada de dia). O grafo de conflito resultante é colorido pelo método guloso Welsh-Powell (ordena por grau decrescente, atribui a menor cor livre) — cada cor final vira uma "VM sugerida".

!

É uma sugestão para avaliação, não uma ação automática: não considera picos acima do P95, licenças/aplicações específicas de cada máquina, nem janelas de manutenção. O texto de caveat retornado pelo próprio algoritmo é exibido literalmente na UI (Visão Operacional → Consolidação de VMs).

Modelo de dados#

Vocabulário de 11 estados operacionais#

Cada ocorrência esperada de agenda (expected_run) recebe exatamente um destes estados via ScheduleMatcher._run_state. É o vocabulário usado em toda a UI (badges, filtros, Central de Alertas).

AGUARDANDOainda dentro da tolerância de início — sem alerta
EXECUTANDOreservado para telemetria ao vivo; nunca atribuído por este modelo (baseado em logs pós-execução)
SUCESSOconcluiu dentro de todos os limites — sem alerta
ATRASADAATENÇÃO início além da tolerância
NAO_INICIOUCRÍTICO passou do deadline sem nenhuma execução casada
DURACAO_ANORMALATENÇÃO duração classificada como CRÍTICA
SLA_EM_RISCOALTO sem execução iniciada e restam ≤25% do prazo até o deadline
SLA_ESTOURADOCRÍTICO concluiu depois do deadline
VM_DEGRADADAALTO overlay: VM primária em saúde CRITICAL enquanto a RPA estaria AGUARDANDO/SUCESSO
ERROALTO execução terminou com status ERROR
WARNINGATENÇÃO execução terminou com status WARNING

A severidade vem do dicionário STATE_SEVERITY em server.py — estados sem entrada ali (AGUARDANDO, EXECUTANDO, SUCESSO) nunca geram alerta na Central de Alertas.

Padrão de alias e sequência de boot#

Depois das 14 classes, dashboard-app.js declara ~65 const de alias — um por função que existia solta no arquivo original — e só então executa a sequência de boot. A ordem importa: em JavaScript, uma referência a um identificador de topo dentro do corpo de uma função é resolvida em tempo de chamada, não em tempo de definição — então, por construção, todo alias já existe no momento em que qualquer método é de fato invocado (sempre depois de o arquivo inteiro ter executado).

js// depois de TODAS as classes definidas:
const escapeHtml = Fmt.escapeHtml;
const goToPage   = NavigationController.goToPage;
const renderAll  = RpaOpsApp.renderAll;
const init       = RpaOpsApp.init;
// … (~65 no total — ver arquivo para a lista completa)

// BOOT — só roda no navegador, e só se os dados carregaram de verdade
// (window.INDEX_DATA/OBS_DATA nulos = Handler._send_data_error reportou uma
// falha — ver Empacotamento/Robustez — nesse caso não há o que renderizar,
// e a tela de carregamento inicial de index.html já mostra o erro real)
let DATA;                                   // variável solta, nunca propriedade de classe
const chartRegistry = ChartService.registry;

if (typeof window !== 'undefined' && typeof document !== 'undefined' && window.INDEX_DATA && window.OBS_DATA) {
    DATA = window.INDEX_DATA;
    DATA.auditExecutions = buildAuditExecutions(window.OBS_DATA);
    window.ACTIVE_EXECUTION_ID = DATA.executionDetail?.executionId ?? DATA.timeline?.[0]?.executionId ?? null;
    NavigationController.bindGlobalControls();
    window.RPA_INCREMENTAL_REFRESH = () => reloadData(DATA.loadStats?.mode || '90d');
    init();
    window.__hideInitialLoadOverlay?.();    // só esconde depois do 1º render completo — nunca antes
}

// export para test_dashboard.js via Node — no-op no navegador
if (typeof module !== 'undefined' && module.exports) {
    module.exports = { Fmt, ChartService, RegistryPage };
}
!

DATA é uma let de topo genuína — não uma propriedade de classe — de propósito: é reatribuída por nome (DATA = window.INDEX_DATA) em RpaDataStore.reloadData e lida por nome em dezenas de métodos das classes *Page. Movê-la para dentro de uma classe (mesmo como static) quebraria essa reatribuição silenciosamente, porque os métodos continuariam lendo o identificador de topo DATA, não a propriedade da classe.

Regra prática: ao adicionar uma função de topo nova em dashboard-app.js, decida se ela pertence a uma classe existente (o caso comum) e adicione o alias correspondente logo no bloco de aliases — nunca crie uma função solta fora desse padrão, ou aa-integration.js pode perder acesso a ela silenciosamente caso venha a depender dela no futuro.

Tela de carregamento inicial (2026-09-28)

Os dois <script src> de dados (observability-data.js/index-data.js) são bloqueantes — o navegador só continua depois que o servidor termina de montar o dataset inteiro. Em produção (muito mais arquivos, log numa pasta de rede) isso pode levar bem mais tempo que no dataset sintético local, e sem feedback nenhum a aba parece travada — sintoma real relatado durante o deploy corporativo. Um <script> inline no topo do <body> de index.html (antes de qualquer tag bloqueante) resolve isso sem tocar na arquitetura de boot: mostra um overlay de tela cheia (#initialLoadOverlay) e sonda /api/load-status — o mesmo endpoint que já alimenta a barra de "Recarregar dados" — numa requisição paralela e independente, enquanto o carregamento bloqueante ainda está em andamento. Funciona porque o servidor atende cada requisição numa thread própria (ThreadingHTTPServer): a thread que monta o dataset atualiza _build_status a cada fase, e a thread da sondagem lê esse mesmo dicionário compartilhado.

Duas auditorias de segurança desta aplicação (mesmo sendo 127.0.0.1-only) já encontraram e corrigiram vulnerabilidades reais e comprovadas com PoC: 4 na primeira rodada, e mais 3 MEDIUM em 2026-09-27 (SSRF via redirecionamento não revalidado, SSRF via TOCTOU/DNS rebinding, XSS armazenado em execution_id) — nenhuma exigiu o servidor exposto na rede: todas exploráveis a partir do próprio navegador do operador, ou a partir de quem controla/compromete o Control Room configurado.

Timeout de 10s com erro claro; trava mais velha que 30s é tratada como abandonada e reclamada (corrigido 2026-09-28, ver SECURITY.md).
SSRF na integração AAAutomationAnywhereGateway._resolve_pinned_ip recusa qualquer host que resolva para loopback, link-local ou o endpoint de metadata de nuvem (169.254.169.254) — redes privadas (10/8, 172.16/12, 192.168/16) continuam permitidas de propósito (Control Room on-premises é um caso de uso legítimo). Resolve o host uma única vez e conecta no IP literal já validado via _PinnedHTTPConnection/_PinnedHTTPSConnection (nunca deixa a stdlib resolver de novo) — fecha uma janela de TOCTOU/DNS rebinding em que um domínio com TTL curto podia responder IP público na checagem e loopback/metadata na conexão real, preservando a verificação de certificado TLS correta (server_hostname = host original, não o IP). Cada redirecionamento 3xx do Control Room passa de novo por essa validação antes de ser seguido (_NoFollowRedirectHandler desliga o redirect automático do urllib) — sem isso, um Control Room malicioso/comprometido podia responder 302 Location: http://169.254.169.254/... e o proxy seguia sem checar de novo (corrigido 2026-09-27, ver SECURITY.md).

Empacotamento (executáveis)#

Gera um executável nativo — Windows .exe ou binário macOS — que roda sem precisar de Python instalado na máquina de quem for usar o painel. Formato: uma pasta (dist/RPA_Ops_Monitor/) com o executável dentro, não um arquivo único auto-extraível — abre mais rápido e tem bem menos chance de antivírus/EDR corporativo barrar (o "onefile" do PyInstaller é um padrão conhecido de dropper de malware e dispara falso-positivo com frequência).

shell# macOS
./packaging/build_macos.sh

# Windows (duplo clique, ou via prompt de comando)
packaging\build_windows.bat

PyInstaller não faz cross-compile: cada script só gera o executável do próprio SO. Para gerar os dois sem ter as duas máquinas, use Actions → "Build executáveis (Windows/macOS)" → Run workflow no GitHub — builda nos runners hospedados do próprio GitHub e disponibiliza os dois como artifact pra baixar (.github/workflows/build-executaveis.yml, disparo manual de propósito).

Sem janela de terminal — RPA_Ops_Monitor.log

O spec usa console=False (2026-09-28): o executável abre só o painel, sem terminal atrás. server.py redireciona stdout/stderr para RPA_Ops_Monitor.log (criado ao lado do executável) sempre que sys.frozen é verdadeiro — sem isso, no Windows, sys.stdout vira None nesse modo e o primeiro print() (o próprio banner de inicialização) derrubaria o processo com AttributeError. Esse arquivo é o primeiro lugar a olhar se o painel abrir vazio ou algo parecer errado — tem o mesmo conteúdo que apareceria num console visível, incluindo traceback completo de qualquer erro não tratado.

✓

Falha ao montar o dataset ou ao ler/gravar o Cadastro (pasta inacessível, por exemplo) não derruba mais a conexão silenciosamente — Handler._send_data_error (dataset: /assets/observability-data.js//assets/index-data.js//api/status) e Handler._send_registry_error (Cadastro: /api/registry/rpas, /api/registry/rpas/scan, criar/editar/remover) sempre devolvem HTTP 500 com a mensagem real no corpo, visível no Network tab do DevTools, além de sempre logar o traceback completo (console ou RPA_Ops_Monitor.log). Antes disso, esse erro derrubava a conexão sem nenhuma informação — o painel ficava em branco, ou o formulário só dizia "falha de comunicação", sem nenhuma pista real.

Por que config/logs ficam fora do bundle

RPA_Ops_Monitor.spec embute só os arquivos somente-leitura (HTMLs, assets/ — exceto observability-data.js/index-data.js, o fallback de file:// que o servidor nunca lê, ~15 MB de peso morto — e docs/documentacao.html). config/ e logs/ nunca entram no bundle: um executável do PyInstaller extrai seus dados embutidos para uma pasta temporária (sys._MEIPASS) recriada do zero a cada execução — se o cadastro estivesse ali dentro, qualquer edição feita pelo Cadastro de RPAs se perderia ao fechar o app.

Por isso server.py distingue dois caminhos-base no topo do arquivo:

ConstanteAponta paraContém
BUNDLE_DIRsys._MEIPASS (empacotado) / pasta do script (dev)HTMLs, assets/ — só leitura; é o que Handler serve estaticamente.
ROOTpasta do executável real, via Path(sys.executable).parent (empacotado) / pasta do script (dev)config/, logs/ — graváveis, precisam sobreviver a um rebuild/atualização.
✓

Rodando como python3 server.py (sem empacotar), BUNDLE_DIR e ROOT são a mesma pasta — nenhum comportamento muda para quem usa dessa forma; validado com a suíte de 89 testes de test_server.py passando sem alteração.
