Rodando como Servidor de Rede

Por padrão o RPA Ops Monitor roda só na máquina do próprio usuário (127.0.0.1) e não tem nenhum sistema de login. Este guia é para quem decidiu, de forma consciente, que vários usuários vão acessar o mesmo painel pela rede — e cobre os pré-requisitos e o passo a passo pra fazer isso sem abrir um buraco de segurança na empresa.

Ver SECURITY.md · seção 1 Ver THREAT_MODEL.md Sem autenticação embutida no app

O que este guia é (e não é)#

É para o cenário: uma máquina roda o servidor, várias pessoas acessam pelo navegador. Não é necessário para o cenário mais comum — cada usuário rodando o app na própria máquina, mesmo que os arquivos de log fiquem numa pasta de rede compartilhada. Esse segundo caso já funciona hoje, sem nenhuma mudança de configuração, porque cada instância continua ouvindo só em 127.0.0.1 na própria máquina.

!

O ponto mais importante deste documento: o RPA Ops Monitor não verifica identidade de ninguém. Toda a segurança de hoje depende de uma única premissa — só o próprio operador consegue alcançar a porta do servidor. Assim que essa premissa deixa de ser verdade (o app aceita conexão de outras máquinas), qualquer pessoa que alcançar a porta consegue ver todos os dados operacionais das RPAs e editar o Cadastro de RPAs, sem nenhum registro de quem fez o quê. Os pré-requisitos abaixo existem pra reconstruir, na frente do app, a barreira que ele mesmo não tem.

Pré-requisitos obrigatórios#

Não pule nenhum item abaixo — cada um cobre uma lacuna real que o app deixa em aberto quando sai de 127.0.0.1.

  • Autenticação na frente do app — Basic Auth com senha forte no mínimo; idealmente integrado ao SSO/Active Directory da empresa. O app em si nunca pergunta usuário/senha.
  • TLS (HTTPS) entre o navegador dos usuários e o que quer que autentique — sem isso, credenciais e dados operacionais trafegam em texto claro na rede.
  • Firewall restringindo a origem — só a sub-rede/VLAN pretendida alcança a porta; nunca deixe a porta alcançável pela internet ou pela rede corporativa inteira sem necessidade.
  • Alguém responsável por manter isso atualizado — certificado TLS expira, senha precisa trocar, e "configurei uma vez e esqueci" é como esse tipo de exposição vira incidente meses depois.
  • Concorrência no Cadastro de RPAs já é tratada — se rpa_metadata.json ficar numa pasta de rede (RPA_MONITOR_CONFIG_ROOT), RpaRegistryStore._locked() serializa as gravações com um arquivo de trava (timeout de 10s, com reclamação automática de trava abandonada) — duas edições simultâneas não corrompem o arquivo nem se perdem silenciosamente. Se a espera exceder 10s, a pessoa vê uma mensagem clara pra tentar de novo, em vez de travar ou perder a alteração.
  • Atualizar o SECURITY.md/THREAT_MODEL.md da sua cópia registrando esse desvio do padrão documentado — data, quem aprovou, e os controles compensatórios (proxy, firewall) que foram colocados.

Variáveis de ambiente#

Todas opcionais — sem definir nenhuma, o comportamento continua sendo o padrão de sempre (só 127.0.0.1).

VariávelPadrãoEfeito
RPA_MONITOR_HOST127.0.0.1Endereço em que o servidor escuta. Só muda isso no método alternativo sem proxy — no método recomendado, o app continua em 127.0.0.1.
RPA_MONITOR_PORT8765Porta do servidor.
RPA_MONITOR_HOSTNAMEbs.rpa-monitor.localhostNome usado para abrir o painel automaticamente. Num deploy de servidor isso importa pouco (ninguém vai estar sentado no servidor vendo o navegador abrir).
RPA_MONITOR_EXTRA_ORIGINS(vazio)Lista separada por vírgula de origens extras aceitas na checagem de CSRF (camada 2) — use esta para declarar o endereço público real que os usuários vão digitar no navegador (ex.: https://rpa-monitor.empresa.local), já que ele normalmente não bate com o formato que o app deriva sozinho (esquema HTTPS, sem porta explícita).
RPA_MONITOR_NO_BROWSER(desligado)Definir com qualquer valor não vazio impede a tentativa de abrir um navegador automaticamente — necessário num servidor sem interface gráfica (senão a tentativa de abrir o navegador gera um traceback inofensivo, mas confuso, no log de inicialização).

Método recomendado: proxy reverso na mesma máquina#

A ideia central: o app nunca muda — continua ouvindo só em 127.0.0.1, exatamente como no uso normal. Quem fica exposto à rede é um proxy reverso (nginx, Caddy, IIS) na mesma máquina, que exige login e HTTPS antes de repassar a requisição pro app local. O app nunca recebe uma conexão direta de fora.

  1. Preparar a máquina servidora

    Qualquer máquina com Python 3 (ou o executável empacotado, se preferir não instalar Python) e um proxy reverso instalado. Não precisa ser potente — a carga é a mesma de hoje, só que servida pra mais gente.

  2. Rodar o app normalmente, sem nenhuma variável nova

    shellpython3 server.py
# ou o executável empacotado — RPA_Ops_Monitor.exe / RPA_Ops_Monitor
# segue ouvindo só em 127.0.0.1, igual sempre

  3. Configurar o proxy com TLS + autenticação

    Exemplo com nginx e Basic Auth (adapte para Caddy/IIS ou para o SSO da empresa, se disponível):

    nginxserver {
    listen 443 ssl;
    server_name rpa-monitor.empresa.local;
    ssl_certificate     /caminho/para/cert.pem;
    ssl_certificate_key /caminho/para/key.pem;

    auth_basic           "RPA Ops Monitor";
    auth_basic_user_file /etc/nginx/.htpasswd;

    location / {
        proxy_pass http://127.0.0.1:8765;
        proxy_set_header Host $host;
        # NUNCA reescreva o header Origin aqui — o app usa ele pra
        # validar CSRF. Deixe o navegador mandar o Origin real.
    }
}
    !

    Gere o .htpasswd com uma senha forte e única (htpasswd -c /etc/nginx/.htpasswd usuario) — nunca reaproveite uma senha de outro sistema da empresa aqui.

  4. Declarar a origem pública real pro app

    O navegador vai mandar Origin: https://rpa-monitor.empresa.local (HTTPS, sem porta) — declare isso antes de subir o app:

    shellRPA_MONITOR_EXTRA_ORIGINS=https://rpa-monitor.empresa.local python3 server.py

  5. Firewall

    Libere a porta 443 (do proxy) só pra sub-rede/VLAN pretendida. A porta 8765 (do app) não precisa — e não deve — estar acessível de fora da própria máquina, já que só o proxy fala com ela.

✓

Nesse modelo, mesmo que alguém descubra a porta 8765 na rede, ela simplesmente não responde — só aceita conexão vinda da própria máquina (do proxy). A superfície de ataque real é o proxy, que é um software desenhado e mantido especificamente pra ficar exposto e autenticar gente.

Alternativa sem proxy (menos recomendada)#

Se um proxy reverso realmente não for viável (ex.: teste rápido numa rede já totalmente isolada e de confiança, tipo uma VLAN de laboratório sem usuário externo), dá pra fazer o app escutar direto na rede — mas sem autenticação nenhuma, então só faça isso numa rede onde "qualquer um que alcançar essa VLAN já é confiável" seja literalmente verdade.

shellRPA_MONITOR_HOST=0.0.0.0 \
RPA_MONITOR_HOSTNAME=192.168.1.50 \
RPA_MONITOR_NO_BROWSER=1 \
python3 server.py

O startup vai imprimir um aviso grande no console confirmando que o app não está mais restrito a loopback — isso é de propósito, pra ninguém subir isso sem perceber.

!

Sem proxy, qualquer máquina que alcançar 192.168.1.50:8765 tem acesso completo de leitura e escrita ao painel, sem login. Prefira sempre o método recomendado.

Testar antes de liberar#

  • Acesse a partir de outra máquina na rede (não a servidora) e confirme que o login do proxy é exigido antes de qualquer coisa do painel aparecer.
  • Confirme que as ações que mudam estado funcionam (ex.: editar uma RPA no Cadastro, clicar "Recarregar dados") — se RPA_MONITOR_EXTRA_ORIGINS estiver errado, elas falham com CSRF_CHECK_FAILED/403 mesmo com o resto funcionando.
  • Tente acessar a porta do app (8765) diretamente, pulando o proxy — se conseguir, o firewall não está configurado corretamente.
  • Combine com quem for usar: qualquer edição no Cadastro de RPAs agora é compartilhada entre todo mundo, em tempo real.

Como voltar atrás#

Pare o processo, remova todas as variáveis RPA_MONITOR_* do ambiente (ou simplesmente não as defina mais) e rode python3 server.py normalmente — volta a escutar só em 127.0.0.1, o padrão de fábrica. Nenhuma mudança de código é necessária para reverter; tudo aqui é opt-in via variável de ambiente.

O que isso NÃO resolve#

  • Autorização granular — o Basic Auth do proxy dá acesso completo (tudo ou nada) a quem passar; não existe "usuário só leitura" vs. "usuário que edita o Cadastro" dentro do próprio app.
  • Auditoria de quem fez o quê — o app não registra qual usuário autenticado fez uma mudança no Cadastro de RPAs (só o proxy sabe quem autenticou, e só se você configurar log de acesso nele).
  • Alta concorrência — a trava de escrita do Cadastro (RpaRegistryStore._locked) é um arquivo comum, não um lock distribuído de verdade; serializa bem algumas pessoas fazendo mudanças esporádicas, não um cenário de muitas gravações simultâneas (ver SECURITY.md).
  • Integração com Automation Anywhere mais exposta — qualquer usuário autenticado no proxy também consegue usar o proxy da integração AA deste servidor para falar com a Control Room configurada.
